## Design Specificity Verdict

### LLM assessment

界面明显为 Mailshop 的跨境选品与 Shopify 导入流程定制，任务工作台、来源图片、1688 结果和 Shopify 店铺导航构成了真实产品特征，不是完全可替换的通用后台。最大问题是这些产品特征被塞进了一个偏通用的“深色侧栏 + 白色卡片 + 密集表单”框架，匹配证据和导入决策的优先级没有在视觉上被充分拉开。

### Deterministic scan

`detect.mjs --json web` 发现 307 项：

- 233 项 `design-system-font-size`：大量 9/11/12/14px 未出现在 DESIGN.md 类型阶梯中。
- 52 项 `design-system-radius`：出现 3/4/6/8/99/999px 等未登记圆角。
- 13 项 `side-tab`：在 `web/src/styles.css` 的 61、944、988、1799、4718、5528、5842、5855、5974、6006、6008、6110 行附近使用 3-4px 侧边强调线。
- 9 项 `design-system-color`：出现 DESIGN.md 未登记的 rgba 颜色。

检测器自身处于降级模式：缺少 `htmlparser2`、`css-select`、`css-tree`、`domutils`，未执行完整选择器匹配和计算对比度，因此结果是下限而不是通过证明。侧边线提示部分与现有状态条设计相符，不能全部视为错误；真正的问题是其使用过于分散，削弱了颜色的稀缺性。

## Overall Impression

这是一个业务逻辑已经成形、视觉系统也有明确意图的运营后台。当前单个页面看起来可靠，但连续工作时会感到“每个区块都在说话”：用户需要自己判断哪个是下一步、哪些信息只是证据、哪些按钮会消耗积分或写入 Shopify。最大的机会是把界面从“信息齐全”推进到“决策顺序清晰”。

## What's Working

1. 任务工作台把来源图、查询参数、结果和运行历史放在同一上下文中，符合真实找货判断，不强迫用户在多个页面间来回切换。
2. 深色侧栏、浅灰绿画布、绿色行动色和蓝/琥珀/珊瑚状态色形成了适合长时间操作的基础视觉语言。
3. React 中已使用 lucide 图标、ARIA label、focus-visible、loading/error/success 等基础状态，说明交互骨架并非只做了静态展示。

## Priority Issues

### [P1] 关键工作区缺少明确的决策主线

**Why it matters:** 图片选择、参数填写、搜索、候选结果、匹配状态和 Shopify 导入同时出现，用户需要在多个局部标题和颜色中重建流程顺序，增加误操作和漏审风险。

**Fix:** 将工作台明确分成“1 选择来源图 → 2 设置搜索 → 3 比较候选 → 4 导入 Shopify”四个带完成态的阶段；每个阶段只保留一个主按钮，候选卡中把“匹配证据、匹配状态、导入动作”固定为同一信息组。

**Suggested command:** `$impeccable layout`

### [P1] 小字号和高密度边框降低可读性

**Why it matters:** 9-12px 文本大量承载状态、来源、SKU、参数和辅助说明，长时间使用或浏览器放大时扫描成本高，也放大了移动端溢出风险。

**Fix:** 统一正文最小字号，机器数据使用 mono 但不承担关键解释；把 9px 标签收敛为少数元数据场景，建立 12/13/15/21px 的稳定层级，并删除不必要的边框和侧边色条。

**Suggested command:** `$impeccable typeset`

### [P1] 导入与积分风险缺少操作前预检

**Why it matters:** 搜图会扣积分，导入会写入 Shopify，重复 URL 和批量失败都是真实成本。用户在点击主按钮前看不到统一的影响摘要，容易把“搜索”“匹配”“导入”混为一谈。

**Fix:** 在搜索和批量导入按钮旁显示预计积分、目标店铺、有效/无效记录数和重复项；对 Shopify 导入提供最终确认摘要，并允许逐行查看失败原因而不丢失有效行。

**Suggested command:** `$impeccable harden`

### [P2] 错误恢复离开了错误发生的位置

**Why it matters:** 全局 ErrorDialog 能告诉用户失败了，但不能稳定地告诉用户哪张图、哪一轮、哪一行出错，也不一定提供可执行的下一步。

**Fix:** 保留全局兜底，同时在表单、搜图轮次、批量预览行内显示错误；错误文案采用“发生了什么 + 怎么修复 + 重试/跳过”结构，并保留用户已输入内容。

**Suggested command:** `$impeccable clarify`

### [P2] 移动端是压缩版桌面工作台

**Why it matters:** 任务工作区包含三列、结果卡、运行历史和批量面板，窄屏时即使能滚动，也很难保持来源图与候选结果的比较关系；移动用户也更难触达顶部主动作。

**Fix:** 移动端改为单列步骤流，固定底部主操作栏；把来源图选择和候选比较做成可横滑的独立区域，批量导入改为全屏面板而非桌面下拉浮层。

**Suggested command:** `$impeccable adapt`

## Persona Red Flags

### Alex（高频运营用户）

- 没有发现针对“搜图、下一轮、导入、归档”的键盘快捷路径。
- 结果卡的操作分散在图片、链接和底部操作行，批量审核/批量导入不足。
- 搜索轮次和候选状态信息完整，但需要多次视觉定位才能完成连续处理。

### Sam（键盘与辅助技术用户）

- 颜色和边框承担了较多状态表达，虽然有文字标签，但状态更新是否被稳定播报需要验证。
- 9-11px 元数据、紧凑按钮和密集三列工作区会让 200% 缩放后的布局更容易拥挤。
- 动态 toast 使用 `role="status"` 是好的基础，但搜图开始、完成、失败和积分变化应有更具体的可访问公告。

### Casey（移动端分心用户）

- 批量导入触发面板锚定在顶部操作区，单手操作和中断恢复都不理想。
- 三列任务工作台需要跨区域记忆当前图片、参数和结果，页面离开后的恢复路径不够明显。
- 关键动作没有形成稳定的底部操作区，容易在长页面中迷失。

## Minor Observations

- “仪表台”可考虑统一为更自然的“工作台”或“概览”，减少用户解释成本。
- `DESIGN.md` 规定的圆角、字号与 CSS 实际值差异较大，应先决定哪些值是有意设计，再同步令牌，避免机械修正破坏已有细节。
- 侧栏导航分组是合理的，但普通用户与管理员看到的结构差异应有更明显的当前范围提示。
- 搜索任务 URL 已同步到地址栏，这是很好的恢复与分享基础，可继续扩展为可保存筛选视图。

## Questions to Consider

- 如果每个工作台始终只突出一个“下一步”，用户是否还能在不牺牲证据可见性的情况下更快完成匹配？
- 哪些信息必须常驻，哪些可以折叠到“查看详情”，以降低连续处理 20 个任务时的疲劳？
- Shopify 导入前，用户最想确认的是目标店铺、候选证据、积分消耗，还是最终商品字段？
